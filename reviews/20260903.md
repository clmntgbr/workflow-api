# Architecture Review — workflow-api

**Date:** 2026-09-03
**Supersedes:** `review copy.md` (2026-08-15)
**Scope:** full codebase vs `.cursor/rules/architecture.mdc`

---

## Executive summary

The layered architecture is still sound: the dependency rule is respected in the two directions
that matter most (`domain` imports nothing outward, `application` imports no adapters), CQRS is
applied consistently, and the outbox/retry/DLQ machinery is correct. Since the previous review the
project also gained a full handler test suite (16 resources) and `*_ports.go` seams for **all 17**
handlers — both were open action items and are now done.

What has degraded is the **edges**: the most recent feature (`header`) was merged without tests,
with a non-standard response envelope, and with a SQL bug that makes one of its two endpoints
return `500` unconditionally. Separately, an auth-middleware registration pattern that has been in
`routes.go` for a while causes the authentication middleware — including a database round-trip — to
execute up to **eleven times per request**.

**Score: 7.5/10** (previous: 8.5/10). The drop is driven by two confirmed runtime defects, not by
structural decay.

## P0 — Confirmed defects

### 1. `GET /api/headers/suggest-values?key=…` always returns 500

`internal/infrastructure/persistence/read/header_query_repository.go:95-115`

The `key` branch builds raw SQL that mixes the Postgres `jsonb` *key-exists* operator `?` with
GORM's positional placeholder `?`:

```sql
WHERE project_id = ? AND headers ? ?
```

GORM cannot distinguish the two — it rewrites **every** `?` into a bind parameter. Two independent
proofs:

- **Arity mismatch.** The statement contains 10 placeholders (5 per `UNION ALL` branch); only 8
  arguments are supplied.
- **Syntax error.** The rendered form is invalid Postgres:

  ```
  db=# PREPARE t AS SELECT 1 FROM endpoints WHERE project_id = $1 AND headers $2 $3;
  ERROR:  syntax error at or near "$2"
  ```

  (The escaped form `headers ? $2` prepares fine, confirming the operator itself is not the issue.)

This path has never worked. It went unnoticed because the `endpoints` and `steps` tables currently
hold **zero** non-empty `headers` values, so every manual test returned an empty result set from the
`key`-less branch.

### 2. The auth middleware runs up to 11× per request

`cmd/api/routes.go` — eleven `setupXxxRoutes` functions each call
`api.Use(container.AuthenticateMiddleware.Protected())` on the *same* `/api` group (lines 53, 59,
70, 81, 91, 97, 107, 114, 125, 135, 140).

Fiber v3 only merges a new `USE` entry into the previous stack entry when that entry is *also* a
`USE` at the same path (`router.go`, `addRoute`):

```go
if l > 0 && app.stack[m][l-1].Path == route.Path && route.use == app.stack[m][l-1].use && … {
    preRoute.Handlers = append(preRoute.Handlers, route.Handlers...)
}
```

Because each function registers concrete routes *between* its `Use()` and the next one, the merge
condition never holds. The result is **11 distinct `USE /api` stack entries**, and every one of them
matching a path executes before the final handler.

Cost per execution (`authenticate_middleware.go:61` → `validate_token.go:29-53`): one JWT
parse-and-verify **plus** one `GetByClerkID` database query. So:

| Route | Auth executions |
|---|---|
| `GET /api/users/me` | 1 |
| `GET /api/endpoints` | 4 |
| `GET /api/headers/suggest` | 5 |
| `GET /api/workflows/:workflowId/activity` | 10 |
| `GET /api/workflows/:workflowId/runs/analytics` | 11 |
| `GET /api/realtime/connection` | 12 (11 group + 1 inline) |

Eleven redundant DB queries on the hottest endpoints.

**Fix** — register the middleware once on a dedicated sub-group and drop every `api.Use(...)`:

```go
func setupAPIRoutes(app *fiber.App, container *di.Container) {
	api := app.Group("/api")

	// Public
	setupPlanRoutes(api, container)

	// Everything below is authenticated, once.
	protected := api.Group("", container.AuthenticateMiddleware.Protected())

	setupSubscriptionRoutes(protected, container)
	setupInvoiceRoutes(protected, container)
	setupUserRoutes(protected, container)
	// … remaining groups
}
```

### 3. Route auth depends on registration order (latent security issue)

`GET /api/plans` is public **only** because `setupPlanRoutes` happens to be invoked at line 35,
before the first `api.Use(Protected())` at line 53. Nothing in the code expresses that intent.

Two failure modes, both silent:

- Moving `setupPlanRoutes` further down makes `/api/plans` authenticated.
- Adding any new `setupXxxRoutes(api, …)` call near the top of `setupAPIRoutes` makes that entire
  resource **publicly reachable**.

The fix in P0-2 removes this class of bug entirely, since public and protected routes land on
explicitly different groups.

## P1 — Architecture-rule violations

### 4. `header` handler shipped without tests

`architecture.mdc` is unambiguous: *"Do not merge handler-only code without the matching test
package updates"*, with a target of 100% statement coverage and a CI floor of 98%.

`internal/interfaces/http/handler/test/` contains 17 packages; **`header/` is not one of them**. It
is the only handler of the 17 with no test package. Required, per the rules:

```
internal/interfaces/http/handler/test/header/
  helpers_test.go   # mocks for headerSuggestHandler + headerValueSuggestHandler, mountRoutes
  handler_test.go   # Suggest / SuggestValues × {Success, MissingActiveProject,
                    #                            InvalidQueryParams, HandlerError}
```

Had these existed, defect P0-1 would have surfaced only at the repository layer — worth adding a
repository-level test too, since handler tests mock the query handler and cannot catch raw-SQL bugs.

### 5. Header endpoints use a bespoke response envelope

`header_handler.go:54-62` and `95-103` return:

```json
{ "success": true, "data": { "items": [...], "page": 1, "limit": 20, "total": 42 } }
```

Nothing else in the codebase does this. The `success` key appears in no other handler, and paginated
lists elsewhere use `paginate.PaginateResponse`:

```json
{ "members": [...], "total": 42, "page": 1, "limit": 20, "totalPages": 3 }
```

The header responses also silently drop `totalPages`. Align them on `PaginateResponse`.

### 6. `interfaces` imports `infrastructure`

| File | Import |
|---|---|
| `internal/interfaces/http/handler/billing_webhook_handler.go:12` | `internal/infrastructure/stripe` |
| `internal/interfaces/http/handler/realtime_ports.go:4` | `internal/infrastructure/centrifugo` |
| `internal/interfaces/http/middleware/billing_webhook_middleware.go` | `github.com/stripe/stripe-go/v82` |

The second is the most damaging: a `*_ports.go` file exists precisely to define a test seam, and this
one types its port against the concrete `centrifugo.ConnectionInfo`. Define the shape in
`presenter/realtime.go` (or `domain/port`) and let the adapter satisfy it. `RealtimeHandler.GetConnection`
is also the only handler returning an infrastructure struct straight to the wire.

### 7. Non-conforming files in `handler/`

The rules allow `*_handler.go`, `*_ports.go`, `*_test_exports.go`, and `test/`. Two files fall outside:

- `internal/interfaces/http/handler/endpoint_import_read.go` — multipart/OpenAPI read helpers
- `internal/interfaces/http/handler/quota_errors.go` — cross-cutting quota → HTTP status mapping

Both are legitimate code in the wrong shape. Either fold them into their handler, or extend the rule
to permit a documented `<resource>_helpers.go` suffix. The latter is probably the honest fix, since
`quota_errors.go` is genuinely shared across handlers and already has tests under `test/quota/`.

### 8. `activity_log_handler.go` queries the DB with unnormalized pagination

`Normalize()` is called at line 74, *after* the query handler runs at lines 64-68. Every other list
handler normalizes first. A request with `?limit=100000` therefore reaches the repository with
`limit=100000` instead of being clamped to 20; `Normalize()` then only corrects the numbers echoed
back in the response envelope. Move the call above the handler invocation.

## P2 — Contract consistency

### 9. Three different list-response shapes

| Shape | Endpoints |
|---|---|
| `PaginateResponse` (`members`/`totalPages`) | workflows, endpoints, runs, invoices, activity, variable-paths, assertion-paths |
| Bare JSON array | plans, projects, steps, connections, variables, available variables, assertions |
| `{success, data:{items}}` | headers/suggest, headers/suggest-values |

Seven / seven / two. The bare arrays are defensible for genuinely unbounded-but-small collections,
but "steps of a workflow" and "variables of a workflow" will grow. Pick one paginated shape and one
documented exception rule.

### 10. Three different error envelopes

`{"message": …}` dominates, but:

- `billing_webhook_handler.go:61-67` uses `{"error": …}`
- `subscription_handler.go:192,228` uses `{"message": …, "errors": "<raw err>"}` — leaks internals
- `user_webhook_handler.go:51,68,90` returns the raw `validator` error, which Fiber's
  `DefaultErrorHandler` renders as **plain text**, not JSON

### 11. `user_webhook_handler.go` bypasses the validation package

It constructs `validator.New()` inline (lines 50, 67, 89) rather than using `validation.Struct`.
Consequences: no camelCase field-name mapping, no `{"message":"Validation failed","errors":{…}}`
envelope, and no `ErrValidationFailed` sentinel, so `FiberErrorHandler` cannot intercept it. This is
the one remaining real instance of the "inconsistent validation" finding from the previous review —
the 11 handlers it flagged have since been fixed and now all call `validation.Struct` or
`validation.BindBody`.

### 12. `PositionRequest` has no validation tags

`dto/step.go:5-8` — `X` and `Y` carry no `validate:` tag, so the `validation.Struct` call in
`StepHandler.UpdatePosition` (`step_handler.go:452`) is a no-op for the only fields that matter.

### 13. `url` is validated on endpoints but not on steps

`dto/endpoint.go:8,34` use `required,url,max=2048`; `dto/step.go:38` uses `required,max=2048` — the
`url` rule is missing. A step can be saved with a malformed URL that the same payload would be
rejected for on an endpoint.

### 14. Route naming inconsistencies

- Same resource, two param names: `/workflows/:id` (CRUD, start, stop) vs `/workflows/:workflowId/…`
  (nested). Likewise `:id` for steps but `:stepId` when a step is a parent segment.
- `/subscription` (singular) alongside `/subscriptions/*` (plural).
- `/headers/suggest` + `/headers/suggest-values` — two endpoints where one would do (see below), and
  `headers` is not a project resource, it is a derived index.

### 15. Redundant `Search` field in the header query structs

`header_handler.go:33-36` and `73-76` embed `paginate.PaginateQuery` — which **already** declares
`Search string \`query:"search"\`` — and then redeclare `Search` at the outer level. The outer field
shadows the embedded one, so `queryParams.PaginateQuery.Search` stays empty while
`queryParams.Search` is populated, and the handler has to pass the two separately. Drop the outer
field and use `queryParams.Search` from the embedded struct.

## Deep dive: the `header` feature

Beyond P0-1, the repository has two more issues worth fixing in the same pass.

**Fragile set-returning-function usage.** The key-less branch
(`header_query_repository.go:120-129`) nests an SRF inside an operator expression:

```sql
SELECT jsonb_object_keys(headers) AS header_key,
       headers->>jsonb_object_keys(headers) AS header_value
```

This *does* work on Postgres 16 — verified, the two SRFs are evaluated in lockstep and pair
correctly — but it relies on target-list SRF semantics that are easy to break and hard to read.
`jsonb_each_text` in a `LATERAL` join is the idiomatic form and is guaranteed.

**Full scans.** Both queries expand every `headers` JSONB in `endpoints` and `steps` for the
project on every keystroke of an autocomplete. Fine at current volume; worth a note, and a reason to
keep `limit` clamped.

**Suggested rewrite** — one query, named parameters (which sidesteps the `?` collision entirely),
`LATERAL jsonb_each_text`, and `key` as an optional filter. This also collapses `Suggest` and
`SuggestValues` into a single endpoint:

```go
const suggestHeadersSQL = `
WITH all_headers AS (
    SELECT h.key AS header_key, h.value AS header_value
    FROM endpoints e, LATERAL jsonb_each_text(e.headers) AS h
    WHERE e.project_id = @projectId
    UNION ALL
    SELECT h.key, h.value
    FROM steps s, LATERAL jsonb_each_text(s.headers) AS h
    WHERE s.project_id = @projectId
)
SELECT header_key, header_value, COUNT(*) AS count
FROM all_headers
WHERE (@key = '' OR header_key = @key)
  AND (@search = '' OR header_key ILIKE @like OR header_value ILIKE @like)
GROUP BY header_key, header_value
ORDER BY count DESC, header_key, header_value
LIMIT @limit OFFSET @offset`

args := map[string]any{
	"projectId": filter.ProjectID,
	"key":       filter.Key,
	"search":    filter.Search,
	"like":      "%" + filter.Search + "%",
	"limit":     query.Limit,
	"offset":    query.Offset(),
}
```

`GET /api/headers/suggest?key=&search=&page=&limit=` returning `{key, value, count}` covers both of
today's use cases; the client filters client-side on `key` when it only needs key names.

## Suggested updates to `architecture.mdc`

1. **Event JSON tags** — carry over the unresolved item from the previous review: domain event
   structs may carry `json:` tags for message serialization; the "no schema tags" rule targets GORM
   only.
2. **Allowed files in `handler/`** — add `<resource>_helpers.go` (or an explicit cross-cutting
   exception) so `quota_errors.go` and `endpoint_import_read.go` have a legal home.
3. **One response envelope** — state which of `PaginateResponse` / bare array applies, and forbid
   ad-hoc `fiber.Map` envelopes in handlers.
4. **One error envelope** — mandate `{"message": …}` (plus optional `errors`, `code`) and forbid
   returning raw error strings from handlers.
5. **Auth registration** — require middleware on an explicit group; forbid repeated `Use()` on a
   shared group, and forbid relying on registration order for a route's auth posture.
6. **Repository tests for raw SQL** — handler tests mock query handlers by design and cannot catch
   SQL defects. Any repository method using `db.Raw` should have an integration test.

## What is genuinely good

Worth stating, because the list above is by nature one-sided:

- **Dependency rule holds.** `go list` over `internal/domain/...` and `internal/application/...`
  finds zero imports of `infrastructure`, `interfaces`, or `cmd`. That is rare and hard to maintain.
- **Ports coverage is complete** — 17/17 handlers, up from partial at the last review.
- **Handler tests exist for 16/17 resources**, with shared `testutil` fixtures and a CI coverage
  floor. Both were action items in the previous review.
- **Validation is now consistent** on request bodies — every `c.Bind().Body` path calls
  `validation.Struct`. The previous review's headline finding is resolved.
- **Outbox, dedup (`event_id`, `handler_name`), retry/DLQ topology, and event versioning** are
  textbook. No `Nack(requeue=true)` anywhere.
- **37 goose migrations** with a runtime schema-drift check (`persistence/schema/check.go`).
